# Регламент підтримки документації (Documentation Maintenance Regime)

**Версія:** 1.0 · **Дата:** 2026-11-15 · **Власник регламенту:** Ant228920 (автор репозиторію)

## 1. Головне правило

> **Зміна коду = зміна документації.**
> Жодна зміна не потрапляє в основну гілку без оновлення зачеплених документів.

Застаріла документація небезпечніша за відсутню: вона створює ілюзію розуміння системи. Тому документи паспорта (README, SDD, ISD, ADR) мають власників і цикли перегляду, а синхронність з кодом перевіряється автоматично.

## 2. Власники та цикли перегляду

Цикли відповідають порогам аудиту (Завдання 1): експлуатаційна документація перевіряється не рідше ніж раз на **90 днів**, архітектурна не рідше ніж раз на **180 днів**.

| Документ | Категорія | Власник | Цикл перегляду | Дата останнього перегляду | Наступний перегляд |
|---|---|---|---|---|---|
| `README.md` | експлуатаційна | Ant228920 | 90 днів | 2026-11-15 | 2027-02-13 |
| `docs/isd.md` | експлуатаційна | Ant228920 | 90 днів | 2026-11-15 | 2027-02-13 |
| `docs/maintenance.md` | експлуатаційна | Ant228920 | 90 днів | 2026-11-15 | 2027-02-13 |
| `docs/sdd.md` | архітектурна | Ant228920 | 180 днів | 2026-11-15 | 2027-05-14 |
| `docs/architecture/adr/0001-*.md` | архітектурна | Ant228920 | 180 днів | 2026-11-15 | 2027-05-14 |

Резервний власник не призначений (див. декларацію Bus Factor у пакеті передачі).

ADR після прийняття не переписуються. Застаріле рішення отримує статус `Superseded by ADR-NNNN`, а нове рішення оформлюється новим номером. «Перегляд» ADR означає перевірку, чи рішення ще чинне.

## 3. Що оновлювати при зміні коду

| Що змінилося | Документи для оновлення |
|---|---|
| Новий або змінений HTTP-маршрут, формат запиту/відповіді | `docs/sdd.md` (розділ 5), `README.md` (якщо видимо користувачу) |
| Новий компонент, модуль чи залежність між модулями | `docs/sdd.md` (діаграма й розділ 3) |
| Зміна моделей або таблиць | `docs/sdd.md` (розділ 4) |
| Зміна `docker-compose.yml`, `Dockerfile`, змінних середовища | `docs/isd.md`, `.env.example` |
| Зміна порядку запуску сервісів (`depends_on`) | `docs/isd.md` (таблиця «Залежності запуску») |
| Зміна CI/CD | `docs/isd.md` (розділ 4) |
| Нове архітектурне рішення | новий ADR; застарілий отримує статус Superseded |
| Будь-яка з вищеперелічених змін | дата в таблиці розділу 2 цього документа |

## 4. Автоматична перевірка

Скрипт `tools/doc_drift_check.py` звіряє код і документацію:

- кожен маршрут із коду є в `docs/sdd.md`;
- кожен сервіс compose має розділ у `docs/isd.md`;
- `depends_on` у compose збігається з таблицею «Залежності запуску».

```bash
python tools/doc_drift_check.py     # код завершення 0 = OK, 1 = дрейф
```

Той самий скрипт запускає GitHub Actions (`.github/workflows/docs-drift.yml`) на кожен `push` і `pull_request`. Збірка з червоним статусом означає, що документація відстала від коду.

Обмеження перевірки: вона ловить відсутність маршруту чи сервісу, але не перевіряє змісту опису. Зміст перевіряє власник під час перегляду.

## 5. Процедура планового перегляду

1. За 7 днів до дати «Наступний перегляд» власник відкриває документ.
2. Звіряє його з кодом і конфігурацією; запускає `python tools/doc_drift_check.py`.
3. Виправляє розбіжності й оновлює дати в таблиці розділу 2.
4. Фіксує результат комітом `docs(maintenance): review <документ>`.

Метрики актуальності знімаються командами з аудиту (Завдання 1): `git log -1 --format=%cs -- <файл>` та кількість змін коду після останнього оновлення документа.
