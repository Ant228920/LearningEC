# ADR-0002: Звернення до зовнішнього провайдера курсів — retry з backoff і статичний fallback

| Поле | Значення |
|---|---|
| **Номер** | 0002 |
| **Статус** | Accepted |
| **Дата рішення** | 2026-10-04 (коміт `96046a0`, «complex code»); реалізацію переоформлено в незмінні Value Objects 2026-11-01 (коміти `d2dcdcb`, `b1315cc`) без зміни самого рішення |
| **Автор** | автор репозиторію |
| **Пов'язано** | [SDD C4, C2](../../sdd.md#31-currency_api--контейнер-застосунку), [ADR-0001](0001-nbu-sync-via-cron-into-postgres.md) |

## Контекст
Якщо валюти немає в локальній базі, `currency_api` запитує курс у зовнішнього провайдера (`UPSTREAM_PROVIDER_URL`). Провайдер не контролюється системою: він може відповідати повільно, повертати помилки або бути недоступним. Користувачеві краще отримати наближену відповідь із чіткою позначкою, ніж помилку 5xx.

## Розглянуті альтернативи

| Варіант | Переваги | Недоліки |
|---|---|---|
| **A. Без повторів: перша помилка → HTTP 502** | Найпростіше, нічого не приховує | Кожен тимчасовий збій провайдера бачить користувач |
| **B. Повтори з експоненційною паузою, без fallback** | Згладжує короткі збої | При тривалій недоступності все одно помилка |
| **C. Повтори + запасне значення з позначкою деградації** | Сервіс відповідає завжди; клієнт бачить `system_status = degraded_fallback` | Запасні курси можуть бути неточними |
| **D. Circuit breaker (наприклад, бібліотека `pybreaker`/`tenacity`)** | Захищає провайдера від лавини запитів, швидко відсікає збій | Нова залежність, більше конфігурації для одного зовнішнього виклику |
| **E. Кеш останнього успішного курсу замість статичної таблиці** | Точніший fallback | Потрібне сховище кешу й політика застарівання |

## Рішення
Обрано **варіант C**. `RetryPolicy` робить до 3 спроб із паузами 0.1 с і 0.2 с (таймаут запиту 0.4 с, з'єднання 0.2 с). Після вичерпання спроб `get_external_rate_with_fallback` повертає значення зі статичної таблиці `FALLBACK_RATES` (для невідомого коду — `1.0`) і прапорець `used_fallback = True`. Ендпоінт підставляє його у відповідь як `system_status: "degraded_fallback"`. Таблицю й параметри політики зроблено незмінними (`MappingProxyType`, `frozen dataclass`), щоб спільний стан не псувався між запитами.

## Наслідки

**Позитивні**
- Запит завжди завершується відповіддю; деградація явна й машинно читана.
- Час очікування обмежений (до ~1.5 с у найгіршому випадку: 3 × 0.4 с таймауту плюс паузи 0.1 і 0.2 с).
- Поведінка покрита тестами (`test_resilience.py`, `test_immutable_value_objects.py`, `test_mutation_audit.py`).

**Негативні та ризики**
- Статичні курси застаріють; їх треба переглядати вручну.
- Базис таблиці `FALLBACK_RATES` (одиниць валюти за 1 USD) відрізняється від базису бази (гривень за одиницю валюти). Формула `from_rate / to_rate` у fallback-режимі може давати інвертований результат. **Потребує перевірки тестом перед використанням fallback у production.**
- У `docker-compose.yml` змінну `UPSTREAM_PROVIDER_URL` не передано, тож у контейнері використовується `localhost:9999`, і fallback спрацьовує завжди ([ISD, змінні середовища](../../isd.md#змінні-середовища)).
- Затримка до ~1.5 с на кожен запит для валюти, якої немає в базі, поки провайдер недоступний (немає circuit breaker).

**Подальші дії:** розглянути варіанти D і E окремим ADR, якщо fallback використовується часто.
